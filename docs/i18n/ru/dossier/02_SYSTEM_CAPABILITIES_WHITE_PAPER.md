**Продукт:** `sdd-parallel` (`parallel-flow`)  
**Категория:** Architectural & Algorithmic Capabilities White Paper  
**Версия:** 0.1.0  
**Назначение:** Документ второго уровня абстракции для архитекторов, исследователей параллельных систем и технических экспертов. Раскрывает алгоритмическую модель, топологию кодовой базы, механизмы изоляции и предотвращения семантических конфликтов без привязки к строкам кода конкретного языка.

## 1. Фундаментальная модель конфликтов в агентной разработке

В отличие от традиционных систем контроля версий, ориентированных на текстовые строки, `sdd-parallel` формализует два принципиально разных типа конфликтов при параллельной работе ИИ-агентов:

```mermaid
flowchart TD
    subgraph K1["Конфликт 1-го рода (Синтаксический)"]
        A1["Задача A пишет в File_X"]
        A2["Задача B пишет в File_X"]
        A1 --- A2
        C1["Git Merge Conflict: W(A) ∩ W(B) ≠ ∅"]
    end

    subgraph K2["Конфликт 2-го рода (Семантический / Радиус поражения)"]
        B1["Задача A меняет сигнатуру в File_X\n(ReturnType: str -> str | None)"]
        B2["Задача B вызывает метод из File_X\n(внутри своего File_Y)"]
        B1 -.->|Семантический радиус I(A)| B2
        C2["Скрытая поломка: Git Merge успешен, но mypy / pytest падают!\nW(A) ∩ I(B) ≠ ∅"]
    end
```

### 1.1. Конфликт 1-го рода ($W_A \cap W_B \neq \emptyset$)
Прямое пересечение множеств файлов, которые задачи модифицируют или создают. Если две задачи пишут в один стандартный файл, их параллельное исполнение в разных ветках приведет к необходимости ручного разрешения конфликта слияния в Git.

### 1.2. Конфликт 2-го рода ($W_A \cap I_B \neq \emptyset$ или $W_B \cap I_A \neq \emptyset$)
Пересечение множества изменяемых файлов одной задачи с **семантическим радиусом поражения (Impact Radius)** другой задачи.
- *Пример:* Задача $A$ модифицирует сигнатуру функции или поведение схемы данных в файле $F_1$. Задача $B$ в своем рабочем дереве разрабатывает фичу в файле $F_2$, зависящем от $F_1$.
- Обе ветки коммитятся без синтаксических конфликтов Git. Локальные тесты в обеих ветках проходят.
- Однако при слиянии веток система получает несовместимость типов данных или нарушение бизнес-инвариантов.
`sdd-parallel` — первый харнесс, который делает этот конфликт детерминированно невозможным на этапе планирования.

## 2. Трехмерная таксономия файлов кодовой базы

Любой проект состоит из разнородных файлов. Наивные блокировщики файлов («один файл — одна блокировка») парализуют параллелизм. `sdd-parallel` классифицирует файлы репозитория на три роли:

```
               ┌────────────────────────────────────────────────────────┐
               │                  ФАЙЛЫ РЕПОЗИТОРИЯ                     │
               └───────────────────────────┬────────────────────────────┘
                                           │
         ┌─────────────────────────────────┼─────────────────────────────────┐
         ▼                                 ▼                                 ▼
┌───────────────────┐             ┌───────────────────┐             ┌───────────────────┐
│    SPINE LOCK     │             │ ADDITIVE REGISTRY │             │  STANDARD MODULE  │
│  (Схемный хребет) │             │ (Точка расширения)│             │ (Бизнес-логика)   │
├───────────────────┤             ├───────────────────┤             ├───────────────────┤
│ Схемы БД, модели  │             │ CLI команды,      │             │ Обычные функции,  │
│ IR, миграции,     │             │ реестры MCP,      │             │ хэндлеры, изолиро-│
│ глобальные типы   │             │ __init__.__all__  │             │ ванные модули     │
├───────────────────┤             ├───────────────────┤             ├───────────────────┤
│ ПРАВИЛО:          │             │ ПРАВИЛО:          │             │ ПРАВИЛО:          │
│ Строго последо-   │             │ Параллельно       │             │ Запрет $W_A \cap W_B$,│
│ вательно (цепочка)│             │ допустимо (merge) │             │ проверка $I(T)$   │
└───────────────────┘             └───────────────────┘             └───────────────────┘
```

1. **`Spine Lock` (Схемные ядра):**
   Файлы, определяющие фундаментальную структуру данных (миграции БД, версии схем, канонические контракты). Любая модификация `Spine`-файла выстраивается планировщиком в строгую последовательную цепочку зависимостей. Задачи одной цепочки никогда не ставятся в одну волну.
2. **`Additive Registry` (Разделяемые аддитивные реестры):**
   Крупные файлы-хабы, куда различные независимые фичи добавляют строчки регистрации (например, декларация CLI-команд, экспорты `__all__`, реестр MCP-инструментов).
   `sdd-parallel` разрешает параллельным задачам одновременно вносить аддитивные изменения в такие файлы, изолируя их по именам функций и барьерно объединяя их на чекпоинте.
3. **`Standard Module` (Стандартные модули):**
   Файлы прикладной логики. Для них действует классический запрет на пересечение $W_A \cap W_B$ и проверка радиуса поражения $I(T)$.

### 2.1. Алгоритмический конвейер детекции ролей (`ASTHotspotScanner` — 3 прохода без хардкода)

В отличие от примитивных оркестраторов, полагающихся на зашитые списки имен файлов конкретных фреймворков (`views.py`, `routers/`, `db.py`), `sdd-parallel` соблюдает **Инвариант 7 (Anti-Overfitting & Invariant-First Architecture)**. Роль каждого модуля вычисляется статическим 3-проходным анализатором синтаксического дерева (`src/sdd_parallel/ast_scanner.py`) без запуска кода:

| Проход | Что анализируется в AST | Константы, узлы и математический критерий |
| :--- | :--- | :--- |
| **Проход 1: Сигнатурный разбор** | Парсинг исходного текста в `ast.Module` и поиск маркеров версионирования схем данных и миграций | `_SPINE_KEYWORDS = ("SCHEMA_VERSION", "auto_migrate", "_migrate_v")` $\to$ взводит флаг `has_schema_version = True` |
| **Проход 2: Ориентированный граф импортов и декораторы** | Обход узлов `ast.Import`, `ast.ImportFrom`, `ast.FunctionDef`, `ast.AsyncFunctionDef` | 1. Строит рёбра `imports` и вычисляет входящую степень узла (**In-Degree / Fan-In**: `len(meta.imported_by)`).<br>2. Проверяет `decorator_list` на паттерны регистрации: `_ADDITIVE_DECORATORS = ("command", "tool", "get", "post", "put", "delete", "patch", "include_router", "register", "route")`. |
| **Проход 3: Детерминированная атрибуция `FileRole`** | Иерархическая классификация с приоритетом безопасности (`SPINE > ADDITIVE_REGISTRY > STANDARD`) | 1. Тестовые пути (`tests/`, `test_*.py`, `*_test.py`) $\to$ всегда `STANDARD`.<br>2. **`SPINE`**, если `has_schema_version == True` $\lor$ имя файла `{"models.py", "schema.py"}` $\lor$ **топологическая центральность $\text{In-Degree} \ge 5$**.<br>3. **`ADDITIVE_REGISTRY`**, если `has_registry_decorators == True` $\lor$ точка сборки `{"cli.py", "__init__.py"}` $\lor$ `*/mcp/server.py`.<br>4. **`STANDARD`** — все остальные модули бизнес-логики. |

## 3. Движок статического анализа и взвешенного радиуса поражения

Для расчета семантического радиуса поражения $I(T_i)$ оркестратор использует гибридный конвейер:

1. **AST Hotspot Scanner:**
   Быстрый статический проход по абстрактному синтаксическому дереву кодовой базы. Определяет декларации классов, функций, декораторов и выявляет файлы, классифицируемые как `Spine Lock` или `Additive Registry`.
2. **Графовый анализатор вызовов и зависимостей (Call Graph Sidecar):**
   Построение статического графа связей между символами кодовой базы по рёбрам:
   - `CALLS` (вес = 1.0)
   - `INHERITS` / `IMPLEMENTS` (вес = 0.9)
   - `TESTED_BY` (вес = 0.8)
   - `IMPORTS_FROM` (вес = 0.7)
3. **Формула затухания радиуса поражения:**
   Взвешенный радиус поражения $I(T)$ вычисляется как транзитивное замыкание символов с экспоненциальным затуханием по глубине $d$:
   $$\text{Score}(v) = \text{Score}(u) \cdot w(u, v) \cdot \gamma^d, \quad \gamma = 0.7$$
   Отсечение шума производится по строгому порогу $\text{Score} \ge 0.5$ с фильтрацией прямых неразрешенных вызовов (`resolution="direct"`), что исключает ложные срабатывания на общеупотребительные имена методов (`.get()`, `.close()`).

## 4. Детерминированный BSP-планировщик волн (Bulk Synchronous Parallel)

Планирование параллельных потоков не отдается на откуп эвристикам LLM, а выполняется детерминированным математическим планировщиком:

```
[Входные задачи спринта / бэклога]
               │
               ▼
   [Построение графа конфликтов]
   - Явные зависимости спеки (EXPLICIT_DEP)
   - Схемный хребет (SPINE_ORDER)
   - Текстовые пересечения (DIRECT_COLLISION)
   - Пересечения радиуса поражения (SEMANTIC_COLLISION)
               │
               ▼
   [Топологическая сортировка и проверка ацикличности (Kahn / Tarjan)]
   (Гарантия 100% покрытия задач и отсутствия дедлоков)
               │
               ▼
   [Упаковка волн (Wave Bin-Packing) под ограничение K параллельных треков]
               │
               ▼
[Результат: WavePlan — детерминированный план фазового исполнения]
```

### Барьерная синхронизация (BSP):
Исполнение разбивается на дискретные волны:
$$\text{Wave } 1 \longrightarrow \text{Merge Checkpoint } 1 \longrightarrow \text{Wave } 2 \longrightarrow \text{Merge Checkpoint } 2 \dots$$
Внутри волны задачи выполняются абсолютно параллельно в изолированных средах. Переход к следующей волне невозможен без прохождения барьерного гейта верификации.

## 5. Изолирующий харнесс: Zero Worktree Pollution & Fixed Track Slots

Большинство систем параллелизации агентов терпят крах из-за засорения файловой системы: создание вспомогательных конфигов или служебных файлов внутри рабочего дерева приводит к падению проверочных команд (`git status --porcelain` возвращает грязный статус, вызывая остановку CI-скриптов и агентных воркфлоу), а постоянное создание/удаление каталогов вызывает ошибку `Missing Folder` в Electron Desktop.

`sdd-parallel` реализует архитектурный паттерн **Zero Worktree Pollution & Fixed Track Slots**:
1. Резервируется параметрический пул постоянных слотов `track-<id>` ($K = \text{max\_tracks}$, по умолчанию `track-a`, `track-b`, `track-c`).
2. Каталоги слотов располагаются по путям `~/.gemini/antigravity/worktrees/<Project>/<track_id>` со стабильными связями (Junctions) в `.worktrees/<track_id>`, обеспечивая константный $O(1)$ footprint и предотвращая сбои UI.
3. Инъекция контекста задачи и контракта скоупа осуществляется в изолированный каталог `.tmp/track-context.md`.
4. Все служебные файлы (`.parallel-lock.json`, пользовательские переопределения воркфлоу) локально маскируются в `.git/worktrees/<name>/info/exclude`.
5. **In-Place Reset:** При смене волн каталог слота не удаляется, а атомарно переключается на свежую ветку через `git checkout -B parallel/<track_id> master ; git clean -fd`.
6. **Результат:** внутри любого параллельного worktree команда `git status --porcelain` возвращает **100% пустой вывод**. Агент и его внутренние линтеры видят идеально чистое рабочее дерево.

## 6. Активный рантайм-барьер (Three-Tier Defense-in-Depth Scope Guard)

Промпты и системные инструкции («пожалуйста, не редактируй чужие файлы») ненадежны: при рефакторинге LLM склонны расширять контекст и случайно модифицировать соседние модули, либо обходить блокировки редактора через запуск скриптов в терминале.

`sdd-parallel` реализует эшелонированную защиту границ:
- **Рубеж 1 (PreToolUse Hook):** перехватывает прямые файловые инструменты агента (`write_file`, `edit_file`, `replace_file_content`). Перед выполнением записи путь целевого файла сопоставляется с манифестом `.parallel-lock.json`:
  - Если файл входит в `allowed_write_globs` или `additive_shared_files` — вызов разрешается.
  - Если файл заблокирован параллельным треком или принадлежит `Spine Lock` — операция мгновенно блокируется с возвратом ошибки `BLAST RADIUS VIOLATION`.
- **Рубеж 2 (Terminal Guard):** перехватывает инструменты командной строки (`Bash`, `run_command`, `cmd`, `powershell`). Вызовы анализируются на попытки записи или деструктивных действий (`>`, `>>`, `sed -i`, `rm`, `python open`) на файлах вне `allowed_write_globs`.
- **Рубеж 3 (OS Read-Only Locks):** на уровне файловой системы ОС на чужие файлы накладывается запрет записи (`chmod a-w`). В связке с `git config core.fileMode false` это физически предотвращает изменение файлов процессами ОС без влияния на статус Git.
- **Контрольный гейт (`verify-wave`):** финальная проверка накопительного `git diff` против `merge-base` и `git status --porcelain` перед слиянием. Предотвращает обход скоупа через промежуточные коммиты ветки; любая несанкционированная модификация немедленно отклоняет мерж.

### 6.1. Почему два файла границ и три эшелона обороны: Когнитивный vs. Исполнительный vs. Ядерный контур

При подготовке слота (`sdd-parallel prepare`) внутрь каждого `git worktree` записываются два разных артефакта: **`.tmp/track-context.md`** и **`.parallel-lock.json`**, а также выставляются системные флаги ОС и Git. Это не дублирование, а строгое разделение уровней управления:

| Эшелон защиты | Артефакт / Механизм | Потребитель | Почему необходим (Что ломается при его отсутствии) |
| :--- | :--- | :--- | :--- |
| **1. Когнитивный контур (Prompt-Level)** | `.tmp/track-context.md` *(Markdown)* | LLM-агент (через `persistent_facts` или системный промпт) | **Экономия токенов и предотвращение циклов повтора.** Модель с первого шага видит свой `Allowed Exclusive Write Scope` и список `Forbidden Files` с человекочитаемыми причинами (`Locked by sibling track-b`). Без этого файла агент вслепую пытается редактировать чужие файлы, натыкается на блок хука и сжигает контекстное окно на бесполезные ретраи. |
| **2. Исполнительный контур (Hook-Level Gate)** | `.parallel-lock.json` *(JSON в корне слота)* | Python-перехватчик `PreToolUse` (`blast_radius_guard.py`) | **Аппаратная защита от галлюцинаций LLM.** Промпт-инжиниринг не даёт 100% гарантии (в 5–12% длинных сессий модель игнорирует текстовые запреты). Хук за `<2 мс` сверяет аргументы `write_to_file`, `edit_file` и `Bash`/`powershell` с JSON-манифестом и блокирует вызов (`DENY`) **до** обращения к диску. |
| **3. Ядерный контур ОС + Гигиена Git (Kernel & VCS Level)** | `chmod a-w` (`FILE_ATTRIBUTE_READONLY`) + `git config --worktree core.fileMode false` | Ядро ОС (Windows NTFS / Linux VFS) и индекс Git | **Защита от прямых шелл-скриптов и сохранение `100% Clean Git Status`.** Даже если процесс попытается открыть чужой файл напрямую в обход хуков IDE, ядро ОС выбросит `PermissionDenied` / `UnauthorizedAccessException`. А локальный флаг `core.fileMode = false` гарантирует, что снятие битов записи не отобразится в `git status --porcelain` как модификация прав `100644 -> 100444`. |

## 7. Монотонный 3-Way Merger и LIFO Rollback Engine

В SDD-фреймворках состояние спринта персистится в файлах (`sprint-status.yaml`, `tasks.md`, `STATE.md`). При параллельной работе несколько агентов одновременно меняют статусы историй в своих ветках. Обычный `git merge` завершается фатальным текстовым конфликтом.

### 7.1. Монотонный 3-Way Merger
`sdd-parallel` предоставляет специализированный трехсторонний резолвер:
- Статусы историй упорядочены в монотонную шкалу прогресса (полурешётку):
  $$\text{backlog} (0) < \text{ready-for-dev} (1) < \text{in-progress} (2) < \text{review} (3) < \text{done} (4)$$
- При слиянии веток трека для каждой задачи выбирается максимальный статус:
  $$\text{Status}_{\text{merged}} = \max(\text{Status}_{\text{base}}, \text{Status}_{\text{ours}}, \text{Status}_{\text{theirs}})$$
- Все комментарии, структура YAML и штампы времени консистентно сохраняются без единого конфликта Git.

### 7.2. LIFO Transactional Wave Rollback Engine
Если волна завершилась неудачно или требует отмены:
- Команда `abort-wave --wave K` удаляет незамерженные ветки треков и снимает блокировки.
- Команда `rollback-wave --wave K [--save-backup]` гарантирует безопасный откат последней волны:
  - Строго соблюдается инвариант LIFO (только последняя подмерженная волна).
  - Автоматически создается неизменяемая резервная ветка `backup/wave-<K>-before-rollback-<timestamp>`.
  - Ветка `master` сбрасывается к коммиту до слияния.
  - Полиморфно сбрасываются статусы историй в SDD-манифестах (`ready-for-dev`) и удаляются сгенерированные спеки.

## 8. Модели оркестрации исполнения

Система поддерживает гибкие режимы работы в зависимости от инфраструктуры:

### Топология А: `Two-Stage Assisted (BMAD Native)` — Рекомендованный стандарт
- Решает проблему ограничения платформы Google Antigravity (`Max Subagent Depth = 1`).
- Оркестратор рассчитывает план, подготавливает постоянные слоты `track-<id>` и выводит матрицу команд запуска через `sdd-parallel run-guide`.
- Оператор открывает постоянные слоты в отдельных окнах и запускает нативный `/bmad-build <story-id>` на уровне `Depth 0`, сохраняя полный цикл 3 независимых линз ревью.
- Оркестратор верифицирует локи и выполняет барьерное слияние с прогоном тестов.

### Топология Б: `Multi-Window Autopilot` (Автономный рой)
- Оркестратор разворачивает worktree и через модуль `AutopilotLauncher` формирует команды запуска для внешних агентов (`antigravity`, `claude-code`, `codex`).
- Каждая сессия выполняется как независимый процесс `Depth 0` с маршрутизацией моделей по `Model Effort Routing` (`High` / `Medium` / `Low`).

### Топология В: `In-Session Flat Dispatch` (Депрекейтирован / Fallback Only)
- Плоский запуск субагентов внутри одного окна диалога. Используется исключительно в окружениях, где запуск отдельных окон или CLI физически невозможен, с явным пониманием потери гарантий многолинзового ревью.
